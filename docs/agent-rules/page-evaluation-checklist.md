# 页面生成校验清单

> 用于 AI 生成或修改页面后的人工 / AI 双重检查。

## 1. 来源与规则

- [ ] 是否登记了原始资料来源。
- [ ] 是否说明页面使用了哪些 foundation。
- [ ] 是否说明页面使用了哪些组件。
- [ ] 是否说明页面涉及哪些一致性流程。
- [ ] 是否记录了无法确认的设计稿 / token / 资产缺口。

## 2. 视觉严谨性

- [ ] 颜色是否来自 token / helper，而不是硬编码。
- [ ] 间距是否来自 foundation scale 或组件规范。
- [ ] 圆角是否符合组件 / 卡片层级。
- [ ] 阴影是否符合动作反馈、浮层、卡片层级之一。
- [ ] 字号、行高、字重是否符合 typography foundation。
- [ ] 图标 / logo 是否真实、清晰、尺寸稳定。

## 3. 交互流程

- [ ] 页面核心任务是否明确。
- [ ] 创建 / 添加 / 查看 / 编辑 / 删除 / 放弃 / 移除 / 二次提示是否归类正确。
- [ ] 主操作是否唯一且突出。
- [ ] 负向操作是否有准确预警或挽留。
- [ ] 提交 / 保存后是否有成功反馈和状态闭环。
- [ ] 关闭 / 返回是否符合当前任务状态。

## 4. 企业软件可用性

页面生成或修改完成后必须过本节。不得因任务被分类为视觉还原而跳过。文案对照 `docs/agent-rules/copywriting.md`；流程动词对照 `consistency-flow-rules.md`；两字按钮空格等例外对照 `button.md`。本轮若无可见文案变更，勾选「本轮无文案变更」即可。

- [ ] 1280-1920 宽度范围是否可用。
- [ ] 当页面使用 Product Shell 时，是否在 `1279px` 与 `1280px` 分别验收最小画布：窄于 `1280px` 由页面横向滚动保护完整结构；表格仅在该最小画布内仍超出内容区时使用自身横向滚动，不能以局部滚动替代页面级横向滚动。
- [ ] 状态是否不只靠颜色表达。
- [ ] 本轮无文案变更；或已按下列项验收用户可见字符串。
- [ ] 辅助说明 / Radio `description` / Tips / `labelHelp` / Alert / 校验报错句末无句号。
- [ ] 中文句使用全角标点；中文句中无半角 `,` `.`。
- [ ] 不用「您 / 你」做人称主语；不用感叹号。
- [ ] 中文与拉丁字母、数字之间按空格规则（`100%` / `90°C` / `100px` / `4:3` 不加空格）。
- [ ] 常规两字按钮中间有空格；链接 / 虚线 / 更多 / 图标 / FAB 不加空格。
- [ ] 流程动词对照一致性流程（创建 / 放弃 / 提交 / 创建成功），不在文案文档另写。
- [ ] 预览免责声明不写进产品辅助文案、字段说明或成功反馈。
- [ ] 空态按「暂无数据 / 0 / - / 未设置」；假千分位 `0,000` 不用；计数占位写成具体数字，不改成 `-`。
- [ ] 表格 / 卡片 / 表单内容是否能扫描。
- [ ] 页面是否避免了装饰性卡片堆叠。

## 5. 组件验收流程

> 组件验收不是只检查 build 或视觉截图，而是检查「Figma / 设计规则 → 组件文档 → Sens token → 真实组件实现 → 真实 Demo → 状态矩阵 → 验收标准」是否闭环。

### 5.1 先验收，后修改

- [ ] 先读取组件文档、设计记录、实现、样式和预览页，再给结论。
- [ ] 在用户确认前，不直接改代码、CSS、token、文档或 changelog。
- [ ] 先说明评分、P0 / P1、最小修改范围、不会改什么和验收方式。
- [ ] 只有用户明确说“确认”“按这个改”“写进去”“可以改文件”后，才写入文件。

### 5.2 三个必答判断题

- [ ] 这个组件是 antd 可承载，还是应该 Sens 自持？说明原因。
- [ ] 真实 Demo 和状态矩阵是否一致？如果不一致，以真实组件 / 真实 Demo 为验收对象。
- [ ] 本次发现的问题，哪些值得沉淀到组件验收标准、conventions 或 foundation？

### 5.3 组件闭环检查

- [ ] 组件边界是否清楚：负责什么，不负责什么。
- [ ] 颜色、字体、圆角、间距、投影是否来自 Sens token / helper，而不是 antd token 或硬编码。
- [ ] 是否存在新增 `.ant-*` 强覆盖、`!important`、硬编码颜色或临时 px。
- [ ] 真实 Demo 是否覆盖主要使用场景，而不是只有状态矩阵。
- [ ] hover / active / focus / disabled / loading / error 等状态是否符合 Sens 规则。
- [ ] keyboard、aria、Tooltip、label、name、close、clear、popup 等行为契约是否闭环。
- [ ] 文档是否和实现一致；是否存在“文档写了但实现没做”或“实现做了但文档没写”。
- [ ] 是否有 Figma 规则未录入，或已录入但未进入真实 Demo 验收。

#### 5.3.1 换肤组件专项验收

- [ ] 功能色与导航色是否完成绿 / 蓝 2×2 组合验收：绿绿、绿蓝、蓝绿、蓝蓝。
- [ ] 是否明确每个颜色属于 `Functional Skin`、`Product Shell Theme`、`Neutral Foundation` 或固定状态色。
- [ ] 是否分别验收真实 Demo 与状态矩阵；矩阵通过不能替代真实交互通过。
- [ ] 是否真实验证 `default`、`hover`、`active`、`focus`、`disabled`、`loading` 等关键状态。
- [ ] Portal 渲染的 Dropdown、Popover、Tooltip、Menu 是否单独验证选中、hover、active 和背景色。
- [ ] `SensSelectDropdown` 未传 `functionalSkin` 时，浮层选中底跟随当前功能色；切蓝后不得仍是神策绿浅底。
- [ ] 换肤后是否检查 DOM 主题属性与实际 CSS 变量是否一致。
- [ ] 是否确认颜色来源为 token / helper，而不是残留固定色或 antd 默认色。
- [ ] 是否区分“视觉通过”“交互通过”“token 来源通过”“控制台 / 承载健康”。
- [ ] 如果存在既有 `findDOMNode` 等控制台警告，是否单独记录为承载债务，不误判为视觉验收失败。
- [ ] 任一主题组合、关键状态或 Portal 浮层未验收时，只能标记为“部分通过”。

#### 5.3.2 真实交互与承载边界专项验收

> 适用于 Select、Dropdown、Tabs、Card、TopNavigation、SideNavigation、Table、Drawer、Modal 等包含真实交互、滚动、浮层或复杂状态的组件。状态矩阵只能证明静态状态覆盖，不能替代真实 Demo 与真实鼠标路径。

- [ ] 真实 Demo 与状态矩阵是否分开验收；矩阵通过不能替代真实交互通过。
- [ ] hover、click、scroll、drag、popup、confirm、clear、close 等行为是否用真实鼠标路径验收，而不是只看静态截图。
- [ ] 触发器、浮层、回显区、操作区是否分别验收状态；不得用其中一层通过替代整体通过。
- [ ] 浮层打开后是否不被页面容器、标题栏、卡片、表格、滚动容器遮盖或裁切。
- [ ] 组件内部滚动是否不破坏主操作区布局；滚动条、箭头、警告图标、清空图标、关闭图标是否能同时存在且互不挤压。
- [ ] 表格单元格是否按内容承载方式验收：定高表格为左右 16px、上下 5px 且固定行高；录入型表格为左右 8px、上下 12px；三行及以上文本、图文或复杂信息使用 Padding 表格（左右 16px、上下 12px）并由内容撑高。
- [ ] 表头固定高；定高、录入型和 Padding 单元格未因全局行高覆盖而互相串扰。内容区从单元格边线内侧测量，长内容不被裁切、重叠或用横向滚动替代纵向扩展。
- [ ] Tips / Tooltip 与 Dropdown / Popover 是否各自按触发规则出现；不能因为下拉打开就自动出现 Tips。
- [ ] 禁用态、加载态是否不出现可交互的 hover / active 视觉反馈。
- [ ] 颜色、间距、圆角、阴影、字体和图标是否逐项说明来源：Design Token / Foundation / 组件规则 / Figma 特例；Figma 特例不得误收为通用 token。
- [ ] 样板间使用基础组件能力时，是否调用正式组件，而不是复制局部 DOM、局部样式或局部状态逻辑。
- [ ] 页面壳、滚动容器、Portal 或响应式收纳会影响组件表现时，是否同时验收基础组件页与样板间页面。
- [ ] 若扫描或评审发现 `.ant-*`、`!important`、事件拦截、overflow 修补、硬编码颜色或临时 px，必须在验收结论中**主动提醒用户**，并区分“本轮新增债务”和“历史债务”。
- [ ] 如果组件为了贴合设计已经持续重写 overflow、popup、keyboard、active、互斥状态、草稿态 / 提交态或复杂事件，应重新评估是否继续 antd 承载，还是进入 Sens 自持。

#### 5.3.3 表单与复合表单专项验收

> 适用于基础 Form、抽屉 / 对话框 / 页面内的复合表单。基础组件规则见 Form、Radio、Checkbox、Select、Input。本节验收组合后的层级、对齐、间距、收纳，以及字段级校验行为。红框 token、上传态、实时校验流程图不在清单展开。

- [ ] 常规单行控件的左右布局：标题与 32px 控件在同一行内垂直居中；控件列之间保持对齐。
- [ ] 含辅助文案、联动内容、嵌套卡片、多行 Radio / Checkbox 或文本域的字段：标题与内容首行顶部对齐，不额外补 32px 对齐盒。
- [ ] 关联 Radio / Checkbox 的首行视觉对齐已通过正式组件能力实现；不得以页面级 padding、负 margin 或绝对定位重复补偿组件内部间距。
- [ ] 辅助文案、报错、计数等关系信息紧贴其解释对象；可位于对象上方或下方，但与所属内容间距均为 4px。
- [ ] 单一内容组的卡片标题未误用灰条或大标题；仅在存在并列信息组、且确需区分层级时使用灰条或更强标题。
- [ ] 灰标题强分组：上一组内容底 → 下一灰标题顶为 40px（默认）；仅当同任务弱分组时用 28px。
- [ ] 普通表单项之间 20px；上下布局标题到控件 8px；Radio / Checkbox 到其关联卡或关联控件 8px（同一字段内，不是下一表单项）。
- [ ] 最后一组内容底 → 底栏按钮 40px；操作区写在 Form 标签外同样成立。
- [ ] 通栏描边卡 / 灰底卡填满控件区；卡内 Input / Select 宽度仍为 `form/control/max-width`（600），窄宽下 `min(100%, 600)`。卡内组标题与字段标题同一左缘，不得再叠 `group-content` 的 16 缩进。
- [ ] 卡片内边距、卡内分割线与内容间距符合规则；分割线上下均为 16px（父级 gap 与分割线 margin 不得叠成 32）。
- [ ] 跨行操作（如“添加全局筛选”）与所属第一列控件共用左对齐线；不得因 antd 容器、`display: contents` 或独立定位产生漂移。
- [ ] Select、多选标签、输入内容和行内动作均在当前控件区或卡片内收纳；窄宽下无截断、溢出或遮挡。
- [ ] 表格型 Popover 的表格填满内容区并保留完整外边框；三列场景自适应分配宽度，没有真实超宽内容时不出现横向滚动。
- [ ] 表格型 Popover 的纵向滚动只作用于表格内容区，标题、分页和操作区保持可见；分页器使用正式 Sens 组件。
- [ ] Popover 内分页器的页码、页数选择器触发器和 Portal 下拉菜单使用同一功能色；换肤后不能只有下拉菜单变色而触发器回退为默认色。
- [ ] Popover、分页器和下拉菜单分别验收 Portal 层级、视口边界、打开 / 关闭和遮挡关系。
- [ ] Checkbox / Radio、图标与同一行主文案视觉居中；链接按钮复用正式 Sens 组件和 Sens 图标，不复制局部 DOM 或另画图标。
- [ ] 连接线、括号、方向性图标等视觉资产使用正式 Sens / Figma 资源；如需翻转，仅翻转对应资源，不翻转改变内容顺序的父容器。
- [ ] 未新增 `.ant-*` 强覆盖、`!important`、负 margin、绝对定位等布局修补；如确有必要，验收结论必须说明原因、范围和后续承载风险。

##### 表单校验

> 来源 Figma `2160:77795`。细则仍归 `form.md`，文案公式归 `copywriting.md`。分步「下一步有错仍可离开」已确认，见下方「分步表单」；本小节不改那条。

- [ ] 默认失焦才出字段报错；不要一输入就报。实时校验只用于字数、密码强度等明确例外。
- [ ] 报错贴在该控件下方：红框 + `feedback-error` + 红文案；有辅助说明时替换，不叠两行。
- [ ] Select / 日期等非输入项同样走框红 + 框下报错，不能只给 Input 做。
- [ ] 点提交：所有失败项同时标出，并滚到第一项。
- [ ] 校验文案按 `copywriting.md`「原因 + 建议动作」，句末无句号。

##### 带锚点长表单

> 规则见 `src/design-system/components/composite/form.md`「带锚点表单」。Anchor 项高、选中色、悬浮卡片圆角归 `anchor.md` 验收；本节只验与表单的组合。三模式任一项未验只能标部分通过。

- [ ] 常驻 / 点击悬浮 / 点击挤压均：贴白板右缘（右边距 0）；灰标题背景右缘与通栏卡右缘 → 锚点视觉左缘 16px（量轨道 / 选中条 / 收起条，不是定位外盒）；灰条与通栏卡同一右缘；通栏卡左缘对齐所属字段标题（条件配置 / 疲劳度），不得再向左拉出；卡内控件与自己的标题左对齐；锚点顶与首个灰标题顶对齐；标题滚出后钉内容区顶 + 16。
- [ ] 常驻与挤压展开：主列让位、灰标题被收窄。点击悬浮展开：叠层遮盖、不挤主列；仅收起条让位。
- [ ] 内容滚动时锚点不随正文滚走。点击锚点项只高亮并滚到对应分组，不跳路由。
- [ ] 收起条 / 悬浮卡片完整可见；未为贴边覆盖 Anchor 右侧锚定。
- [ ] 1280–1920 下三种模式可用；卡内控件 `min(100%, 600)`。
- [ ] 锚点不得挡住产品壳全局菜单。
- [ ] 换肤后选中字和左侧标记跟随当前功能色；portal 到 body 后不得回落神策绿。

##### 分步表单 · 召回规则

> 规则见 `src/design-system/components/composite/form.md`「分步表单」。步骤条本身归 `steps.md`。

- [ ] 召回步顶层标题为 `SensSectionTitle variant="productLine"`；辅助文案走 `description` 同行；补齐规则带 `(选填)`。
- [ ] 专用标题左右 24；描边卡与卡下复选左右 36；标题文字与卡片左缘对齐。
- [ ] 「选择可推物品」卡底 → 「补齐规则」标题顶为 40。卡内筛选块与截取块间距 20。
- [ ] 筛选行选择器间距 8；且/或连接器跨行，不把行距撑开。第三段为选择器+数字拼缝组合框。
- [ ] 且/或「且」块跟随 `--sens-skin-primary`；「或」与竖线保持中性。切蓝后「且」不得仍是神策绿。
- [ ] 截取行文案为「截取 / 条」，不是「规则名称」；卡下复选默认勾选。
- [ ] 步骤条、下一步、上一步都能换步。带着错误离开：报错步为红色数字，不是红对勾。整表提交打回已完成步：红色对勾。
- [ ] 未完成报错悬停：序号底为 `warning-light-background`，数字为 `warning-color`，不是功能色浅底。

#### 5.3.4 表格与复合表格专项验收

> 适用于基础 Table、筛选 / 搜索 / 信息栏 / 录入型 / 交叉表格等复合表格，以及承载长表格的产品壳样板间。基础细则见 `table.md`，复合组合见 `composite/table.md`；本节只验组合闭环、对齐、状态和页面承载，不替代列配置、真实请求或尚未收录的树 / 嵌套 / 拖拽能力。

- [ ] 表头固定高度、标题不折行；文本列组合靠左，数字、计数、金额、日期等可比较字段组合靠右。
- [ ] 数值列以标题**文字右缘**作为右对齐锚点，逐列与下方数值右缘量对齐；单位、帮助与排序 icon 均不改变该锚点。
- [ ] 排序只由紧跟标题的排序 icon 触发，并实测完整循环「默认 → 升序 → 降序 → 默认」；无排序或仅悬停 icon 时，表头与整列均无激活背景；升序、降序生效后，表头与同列单元格分别使用基础表格规则定义的激活背景。
- [ ] 勾选列区分两类：树表格 / 录入型表格可为“复选框 + 文案”；批量操作必须是独立选择列，左侧 16px、右侧贴边，不把正文列 padding 误套到选择列。
- [ ] 定高、录入型与 padding 型单元格按各自承载规则验收；异步单元格只显示正式 loading，失败态提供可点击刷新并能完成一次刷新闭环。
- [ ] 信息栏按“总条数 / 筛选结果 / 数据更新 / 数据量过大 / 批量操作”的场景与优先级展示；设置列目固定在最右，前置动作仅允许链接按钮，tips 文案为“设置列目”。
- [ ] 筛选表格的搜索框固定 200px、选择器固定 148px；筛选、信息栏、表体与分页的条数 / 状态联动可实际操作验证。
- [ ] 交叉表格按合并单元格的共享关系验收整组 hover / 选中 / 明细展示，不能只给单个格子加局部背景。
- [ ] 长表格样板间同时验证产品壳与表头吸顶互斥：顶导收起后，标题栏与表头二选一吸顶；本样板使用表头吸顶，标题栏应随正文滚走。

### 5.4 承载方式判断口径

- [ ] 低交互组件可以保留 antd 承载。
- [ ] 如果只是颜色、间距、圆角、字体、尺寸调整，可以保留 antd。
- [ ] 如果已经需要重写 keyboard、overflow、popup、drag、editing、active、click wave 或复杂状态分配，应重新评估 Sens 自持。
- [ ] 不为了保留 antd 而持续新增 `.ant-*`、`!important` 或事件拦截。
- [ ] 发现历史 `.ant-*` / `!important` 时，区分“本轮新增”和“历史技术债”。

### 5.5 输出格式

组件验收结论应至少包含：

- 当前评分：x/10。
- 一句话结论。
- 三个判断题答案。
- 已经收口。
- 必须收口 P0。
- 建议收口 P1。
- 可以保留。
- 不建议现在做。
- 如果要改，最小修改范围、改动建议、不改什么和验收方式。
- 最终判断：适合轻收口，还是需要重新评估承载方式。

在以上结论中，换肤相关还应补充：

- [ ] 换肤组合验收结果。
- [ ] 真实 Demo、状态矩阵、Portal 浮层的分别结论。
- [ ] 颜色语义归属。
- [ ] 控制台与承载警告。

### 5.6 评分口径

- 9-10 分：文档、token、真实实现、Demo、状态矩阵、交互和验收规则基本闭环，只剩很小边界。
- 7-8 分：主路径可用，但仍有 1-3 个明确 P0 / P1 需要收口。
- 5-6 分：能展示，但文档、Demo、交互或 token 有明显断层。
- 5 分以下：更像临时样张或 antd 换皮，还没有形成 Sens 组件。
